# EXTRACTION RULES

## 1. What to Extract

EXTRACT clauses with requirements/descriptions:
- ISO style: "4 Context", "4.1 Understanding", "8.5.1 Control of production"

DO NOT EXTRACT section headers from table of contents:
- "1 Introducing The EFQM Model" (no "Criterion X:")
- "2 The EFQM Model" (no "Criterion X:")
- "3 The EFQM Diagnostic Tool" (methodology section)
- "Criterion 2: Organisational Culture & Leadership" (actual criterion)

**Rule**: Look for "Criterion X:" pattern in EFQM or detailed clause text in ISO.
**Skip**: Generic section headers without "Criterion" or detailed requirements.

## 2. Extracting Titles (CRITICAL)

Extract the ACTUAL descriptive title WITHOUT the code/number:

Examples:
- "Criterion 1: Purpose, Vision & Strategy" → code: "1", title_en: "Purpose, Vision & Strategy"
- "4.1 Quality Management System" → code: "4.1", title_en: "Quality Management System"
- "3.1 Customers: Builds Relationships" → code: "3.1", title_en: "Customers: Builds Relationships"
- "8.5.1 Control of production" → code: "8.5.1", title_en: "Control of production"

NEVER include in title:
- "Criterion X", "Sub-criterion X.Y", "Clause X"
- The code itself: "4.1 Quality...", "3.1 Customers..."

Extract ONLY the descriptive part after the code

## 2a. Finding Sub-Clauses

Look for hierarchical numbering patterns:
- "X.Y Title" → code: "X.Y", parent_code: "X"
- "X.Y.Z Title" → code: "X.Y.Z", parent_code: "X.Y"

Examples from any standard:
- "4.1 General requirements" → code: "4.1", parent_code: "4"
- "3.1 Customers" → code: "3.1", parent_code: "3"
- "8.5.1 Control of production" → code: "8.5.1", parent_code: "8.5"

Extract ALL sub-clauses you find, maintaining the hierarchy

## 3. Hierarchy Rules

- Root clauses (top level) → parent_code: null
  * Examples: "4", "5", "Criterion 1", "Criterion 3"

- Sub-clauses → parent_code: the parent's code
  * "4.1" → parent_code: "4"
  * "4.1.2" → parent_code: "4.1"
  * "3.1" → parent_code: "3"

- Use EXACT codes from the document
- Maintain the hierarchy as it appears

ONLY generate checkpoints for TERMINAL clauses (the deepest level without sub-clauses)

- Example: If "5.2.1" has NO sub-clauses, then "5.2.1" MUST have checkpoints
- Parent/intermediate clauses should have checkpoints: []

## 5. Checkpoint Quality
Generate 2-5 meaningful checkpoints per terminal clause:
- Make them specific, actionable, and auditable
- Focus on verification questions ("Is X documented?", "Does Y meet requirements?")
- Include both process and output checks
- Use clear, professional language

## 6. Translations (Arabic)

- Use formal Arabic suitable for quality management contexts
- Maintain technical terminology accuracy
- Keep translations concise and professional

## 7. Stable Keys (CRITICAL - MUST HAVE PROPER PREFIXES)

- ALWAYS use "chk_" prefix for checkpoint stable_keys (e.g., "chk_customer_requirements_doc")
- NEVER start with underscore or number: "_1_3" is WRONG, "clause_1_3_ecosystem" is CORRECT
